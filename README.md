# منصة القهوة V1 — النسخة الخاصة

نسخة بغداد الأولى لمنصة اكتشاف ومقارنة القهوة والمعدات والجهات والمحتوى. هذه
النسخة خاصة وغير معتمدة للنشر العام حتى موافقة مالك المشروع.

## القرارات المثبتة

- السوق الأول: بغداد (`IQ-BGD`).
- الإطلاق العام: متوقف افتراضياً.
- البن الأخضر: مؤجل.
- مكائن التحميص: ضمن V1.
- نموذج التجارة: إحالة خارجية؛ لا سلة ولا دفع ولا طلبات داخلية.
- قاعدة البيانات ومصدر الحقيقة التشغيلي: Supabase.
- الدليل: منظم ومراجع؛ لا يظهر إلا السجل ذو الحالة `published`.
- المفضلة والمقارنة في النسخة الخاصة: محلية على الجهاز، دون حساب عام.

## هيكل التطبيق

- `app/ui/Platform.tsx`: صفحات وتجارب V1 العامة والخاصة.
- `app/api/platform-status`: إعدادات السوق والإطلاق من Supabase.
- `app/api/public-directory`: الجهات المنشورة فقط.
- `app/api/public-products`: المنتجات والمواصفات والعروض المنشورة فقط، مع دعم التصفية حسب النوع والفئة والرابط.
- `app/api/public-search`: بحث موحد في المنتجات والجهات والمصادر والمحتوى المنشور.
- `app/api/public-origins`: الدول والمناطق وعلاقات القهوة المنشورة فقط.
- `app/api/public-content`: المحتوى المنشور وعلاقاته فقط.
- `app/api/rights-request`: استقبال طلبات التصحيح والإزالة والاعتراض والخصوصية.
- `app/api/admin`: جلسة إدارة قصيرة العمر وطابور اعتماد محمي بسياسات RLS.
- `supabase/migrations`: ترقيات قاعدة البيانات اللاحقة للمخطط الأساسي.
- `data`: دفعات البيانات المصححة القابلة للتتبع.
- `docs/Baghdad_Organization_Review_Batch_001_AR.md`: مراجعة أدلة أول دفعة جهات بغداد.
- `docs/Supabase_Advisor_Baseline_AR.md`: خط أساس أمان وأداء قاعدة البيانات.
- `tests`: اختبارات البناء والمسارات وحالة الفشل الآمن.
- `handoff`: دليل التشغيل والاختبار والقبول والفجوات المعروفة.
- `render.yaml`: تعريف خدمة Next.js/Node التجريبية على Render.

## متغيرات التشغيل

تُضبط في بيئة الاستضافة ولا تُحفظ قيمها الحقيقية في المصدر:

```text
SUPABASE_URL
SUPABASE_PUBLISHABLE_KEY
APP_BASE_URL
```

مفتاح `service_role` وكلمة مرور قاعدة البيانات غير مطلوبين داخل التطبيق ويجب
عدم وضعهما في ملفات المشروع أو الواجهة.

## ترتيب قاعدة البيانات

تُشغّل الملفات الموجودة في `supabase/migrations` بالترتيب من `001` إلى `041`.
يوثق `supabase/RECOVERY_MANIFEST.json` الترقيات التي استُرجعت من سجل قاعدة
البيانات بعد انتقال المشروع إلى GitHub، ويتحقق الأمر التالي من سلامة نصوصها:

```bash
npm run verify:migrations
```

الملفان `031a/031b` والملف `037b` يحفظون حدود التنفيذ الأصلية لترقيات Supabase
المستقلة، ولا يمثلون إعادة ترتيب للمخطط.

يثبت `041_phase5_attached_record_contract.sql` نتيجة `attached` في واجهة الربط
القديمة، ويغلق مسار إنشاء المنتجات القديم؛ إنشاء المنتج وتعديله يمران حصراً عبر
عقد Phase 5 الذري مع فحص revision.

الملفات `001`–`005` تنشئ المخطط والتصنيف والتشغيل والمالك ودفعة بغداد، ثم:

1. `006_rights_request_intake.sql` يقوي استقبال طلبات الحقوق.
2. `007_baghdad_batch_001_corrections.sql` يصحح تعارضات دفعة بغداد.
3. `008_supabase_advisor_baseline.sql` يعالج خط أساس مستشار Supabase.
4. `009_baghdad_product_batch_001.sql` يستورد أول دفعة منتجات موثقة وعروضها المحلية بحالة `in_review` فقط.

لا ينشر أي ملف جهة أو منتجاً. تبقى عملية النشر قراراً مستقلاً بعد المراجعة.

صفحات قوائم المنتجات وتفاصيلها مرتبطة بواجهة البيانات العامة. عند عدم وجود
منتجات منشورة تظهر حالة فراغ صريحة، بينما تبقى سجلات المراجعة في قسم معاينة
داخلية منفصل لا يُقدَّم على أنه كتالوج منشور.

## بوابات الجودة

```bash
npm run lint
npm test
```

نجاح البناء لا يساوي موافقة النشر. يجب إبقاء `public_launch_enabled=false` إلى
حين انتهاء مراجعة البيانات والقبول النهائي من المالك.

## الاستضافة

يبني GitHub Actions فرعي `phase5/**` و`main` وطلبات الدمج إلى `main`. يرتبط
Render بالفرع `main` وينشر فقط بعد نجاح فحوص GitHub، مستخدماً خدمة Node في
Frankfurt. تُدخل قيم Supabase في Render عند إنشاء Blueprint ولا تحفظ في Git.
